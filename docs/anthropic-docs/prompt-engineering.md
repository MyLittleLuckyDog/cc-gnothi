# 프롬프트 엔지니어링 레퍼런스

Claude의 최신 모델(Opus 4.7, Opus 4.6, Sonnet 4.6, Haiku 4.5)을 위한 단일 프롬프트 엔지니어링 참조 문서.

---

## 핵심 원칙

**프롬프트 엔지니어링 전 선행 조건**: 성공 기준 정의 → 평가 방법 수립 → 초안 프롬프트 작성. 이 세 가지가 없으면 프롬프트 엔지니어링부터 시작하지 말 것.

**황금 원칙**: 작성한 프롬프트를 업무 맥락이 없는 동료에게 보여줄 것. 동료가 혼란스러워한다면 Claude도 혼란스럽다.

1. **명확하고 직접적으로**: Claude는 명시적 지시에 잘 반응한다. "최선을 다해줘" 같은 막연한 표현 대신 원하는 출력을 구체적으로 기술한다. "above and beyond" 행동을 원하면 명시적으로 요청한다.

2. **맥락을 제공한다**: 지시사항의 이유(why)를 설명하면 Claude가 목표를 더 잘 이해하고 적합한 응답을 생성한다. Claude는 설명에서 일반화할 만큼 충분히 스마트하다.

3. **예시를 활용한다**: 잘 만들어진 예시 3~5개(few-shot/multishot)가 정확성과 일관성을 크게 향상시킨다. 예시는 `<example>` 태그로 감싼다.

4. **긍정적 지시를 우선한다**: "~하지 마라" 대신 원하는 행동을 기술한다. 부정 예시보다 긍정 예시가 더 효과적이다.

## 기법별 가이드

| 기법명 | 언제 쓰나 | 예시 형태 |
|--------|-----------|-----------|
| **XML 태그 구조화** | 지시, 컨텍스트, 예시, 변수 입력이 혼재할 때 | `<instructions>`, `<context>`, `<input>`, `<examples>` |
| **롤 설정 (역할 부여)** | 특정 전문성·톤이 필요할 때 | 시스템 프롬프트: `"You are a helpful coding assistant specializing in Python."` |
| **멀티샷 예시** | 출력 형식·톤·구조를 정확히 제어할 때 | `<examples><example>...</example></examples>` |
| **긴 컨텍스트 구조화** | 20k+ 토큰 문서를 다룰 때 | 문서를 상단에 배치 + `<document index="n">` 태그 + 쿼리를 프롬프트 끝에 위치 |
| **인용 먼저 추출** | 긴 문서에서 정확한 근거 기반 답변이 필요할 때 | "먼저 관련 인용문을 `<quotes>` 태그에 담고, 그 다음 분석을 `<info>` 태그에 담아라" |
| **Thinking 활용** | 멀티스텝 추론, 에이전틱 작업, 복잡한 코딩 | `thinking: {type: "adaptive"}` + effort 파라미터 조합 |
| **프롬프트 체이닝** | 중간 결과를 검사·분기해야 하는 파이프라인 | 초안 생성 → 기준 대비 검토 → 개선 (각 단계 별도 API 호출) |
| **병렬 도구 호출** | 독립적인 여러 작업을 동시에 처리할 때 | "독립적인 도구 호출은 반드시 병렬로 실행하라" 명시 |
| **자기 검증 유도** | 코딩·수학에서 오류 최소화 | "완료 전에 [기준]에 대해 답을 검증하라" |

## Claude 특화 팁

### Effort 파라미터로 추론 깊이 조절

```
max / xhigh → 코딩·에이전틱 (가장 높은 지능)
high         → 지능 민감 작업의 최소 권장치
medium       → 비용 민감 작업
low          → 짧고 단순한 작업, 지연 민감 워크로드
```

- 복잡한 문제에서 얕은 추론이 보이면 → 프롬프트보다 effort 올리기가 우선
- `max`/`xhigh` 사용 시 max output token을 64k 이상으로 설정

### 리터럴 지시 따르기 (Opus 4.7)

Opus 4.7은 이전 모델보다 더 문자 그대로 지시를 따른다. 지시 범위를 명시하지 않으면 첫 번째 항목에만 적용할 수 있다. `"모든 섹션에 이 형식을 적용하라, 첫 번째만이 아니라"` 처럼 범위를 명확히 명시한다.

### 도구 사용 촉진

"제안해줄 수 있어?" → Claude가 제안만 할 수 있다. 실제 변경을 원하면 `"이 함수를 변경해라"` 처럼 명령형으로 작성한다.

적극적 행동 기본값 설정:
```
<default_to_action>
기본적으로 변경사항을 구현하라. 의도가 불명확하면 가장 유용한 행동을 추론하여 진행하라.
</default_to_action>
```

### 응답 형식 제어

- "마크다운 쓰지 마라" 대신 → "산문 단락으로 작성하라"
- XML 형식 지시자 활용: `"산문 섹션을 <smoothly_flowing_prose_paragraphs> 태그 안에 작성하라"`
- 프롬프트 스타일이 출력 스타일에 영향을 준다: 마크다운 없는 프롬프트 → 마크다운 감소

### 에이전틱 코딩에서 과잉 엔지니어링 방지

```
요청된 것만 변경하라. 요청하지 않은 기능, 리팩토링, "개선"은 추가하지 마라.
변경하지 않은 코드에 주석·타입 어노테이션을 추가하지 마라.
현재 작업에 필요한 최소한의 복잡도만 사용하라.
```

### 코드 리뷰 하네스 (Opus 4.7)

모델이 "중요한 이슈만 보고하라"는 지시를 이전 모델보다 충실히 따르므로, recall이 낮아 보일 수 있다. 버그 찾기가 목적이면:
```
찾은 모든 이슈를 보고하라. 확신이 없거나 낮은 심각도라도 필터링하지 마라.
각 발견에 신뢰도와 예상 심각도를 포함하라.
```

## 흔한 실수

| 실수 | 문제 | 개선 방법 |
|------|------|-----------|
| 막연한 지시 | `"Create an analytics dashboard"` | `"Create an analytics dashboard. Include as many relevant features as possible. Go beyond the basics."` |
| 이유 없는 금지 | `"NEVER use ellipses"` | `"TTS 엔진이 줄임표를 발음할 수 없으므로 절대 사용하지 마라"` |
| 과도한 tool 촉진 문구 | `"CRITICAL: 항상 이 도구를 써야 한다"` | `"이 도구를 쓰는 것이 도움이 될 때 사용하라"` (Claude 4.6+는 overtrigger됨) |
| prefill 사용 | Claude 4.6+에서 400 에러 발생 | 시스템 프롬프트에 `"도입 없이 바로 시작하라"` 지시 |
| 쿼리를 문서 앞에 배치 | 긴 컨텍스트 성능 저하 | 문서를 상단, 쿼리를 최하단에 배치 (성능 최대 30% 향상) |
| 부정 예시만 제공 | 원하는 동작보다 피해야 할 동작에 집중 | 올바른 동작의 긍정 예시를 더 많이 제공 |
| thinking budget 수동 설정 유지 | Claude 4.6+에서 deprecated | `thinking: {type: "adaptive"}` + effort 파라미터로 전환 |
| 테스트 통과만을 위한 하드코딩 방지 누락 | Claude가 특정 입력에만 동작하는 코드 작성 | `"모든 유효한 입력에 동작하는 일반 솔루션을 구현하라. 테스트 케이스에만 맞는 하드코딩 금지"` |
