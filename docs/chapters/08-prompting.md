# CC 맥락에서의 프롬프트 작성법

> 이 챕터: CC(Claude Code)에서 사람이 Claude에게 지시하는 방법 — 코딩 에이전트에 최적화된 기법을 다룬다.  
> 최소 버전: v2.1.0

## 개념

CC 프롬프트는 일반 Claude API 프롬프트와 다르다. API는 단발 요청-응답이지만, CC는 **도구 사용 루프**다. Claude가 파일을 읽고, 코드를 실행하고, 결과를 보고, 다시 행동하는 멀티턴 에이전틱 루프 위에서 동작한다.

| 구분 | 일반 Claude API | CC |
|---|---|---|
| 실행 단위 | 단일 메시지 교환 | 도구 호출 루프 (N회 반복) |
| 컨텍스트 소스 | 사용자가 직접 제공 | CLAUDE.md + 파일 탐색 + 도구 결과 |
| 지시 수명 | 해당 요청만 | CLAUDE.md → 세션 전체 |
| 모델 선택 | API 호출 시 지정 | 모델 라우팅 규칙 또는 `/model` 커맨드 |
| Thinking 제어 | `budget_tokens` (deprecated) | `effort` 파라미터 또는 `/effort` 커맨드 |

**핵심 원칙**: 지시가 길수록 준수율이 떨어진다. 자주 쓰는 규칙은 CLAUDE.md에, 일회성 지시는 프롬프트에.

---

## 패턴

### 1. CC 프롬프트의 3요소

효과적인 CC 지시는 세 가지를 명시한다:

| 요소 | 설명 | 예시 |
|---|---|---|
| **목표** | 무엇을 달성해야 하는가 | "인증 모듈을 JWT로 교체하라" |
| **제약** | 건드리지 말아야 할 것 | "테스트 파일은 수정하지 마라" |
| **검증 기준** | 완료를 어떻게 판단하는가 | "기존 테스트가 모두 통과해야 한다" |

```text
# 나쁜 예
"인증 코드를 개선해줘"

# 좋은 예
"src/auth/ 아래 세션 기반 인증을 JWT로 교체하라.
제약: tests/ 디렉토리는 수정하지 마라.
완료 기준: npm test 전체 통과."
```

---

### 2. 명확하고 직접적인 지시

**황금 원칙**: 작성한 프롬프트를 맥락 없는 동료에게 보여줄 것. 동료가 혼란스러워하면 Claude도 혼란스럽다.

| 패턴 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 막연한 요청 | "이 함수를 개선해줘" | "이 함수의 시간 복잡도를 O(n²)에서 O(n log n)으로 낮춰라" |
| 행동 vs 제안 | "어떻게 바꿀 수 있을까?" | "이 함수를 변경하라" |
| 이유 없는 금지 | "절대 console.log를 쓰지 마라" | "프로덕션 코드이므로 console.log 대신 logger.info를 써라" |
| 범위 불명확 | "이 형식을 적용해라" | "모든 섹션에 이 형식을 적용하라, 첫 번째만이 아니라" |

> Opus 4.7은 이전 모델보다 더 문자 그대로 지시를 따른다. 범위를 명시하지 않으면 첫 항목에만 적용할 수 있다.

### 3. XML 태그로 프롬프트 구조화

복잡한 지시에서 XML 태그는 Claude가 내용 유형을 명확히 구분하게 한다.

```xml
<task>
  src/payment/ 아래 결제 플로우를 리팩토링하라.
</task>

<context>
  현재 코드는 Stripe v2 API를 사용 중이다.
  v3로 마이그레이션이 필요하다.
  변경 내역: https://stripe.com/docs/upgrades
</context>

<constraints>
  - tests/ 디렉토리 수정 금지
  - 공개 API 시그니처 변경 금지
  - 기존 에러 코드 유지
</constraints>

<success_criteria>
  1. npm test 전체 통과
  2. Stripe v3 SDK만 사용
  3. TypeScript 오류 없음
</success_criteria>
```

**권장 태그 패턴**:

| 태그 | 용도 |
|---|---|
| `<task>` | 핵심 목표 |
| `<context>` | 배경 정보, 링크, 현재 상태 |
| `<constraints>` | 하면 안 되는 것 |
| `<success_criteria>` | 완료 판단 기준 |
| `<examples>` / `<example>` | 예시 (3~5개 권장) |
| `<documents>` / `<document index="n">` | 긴 참조 문서 |

> 긴 문서를 참조할 때는 문서를 프롬프트 **상단**에, 쿼리를 **하단**에 배치. 최대 30% 성능 향상.

### 4. 적극적 행동 vs 보수적 행동 제어

기본적으로 CC는 파일 수정 전 확인을 요청한다. 이 행동을 CLAUDE.md나 프롬프트에서 조정할 수 있다.

**적극적 행동 (기본 구현):**

```xml
<default_to_action>
기본적으로 변경사항을 구현하라.
의도가 불명확하면 가장 유용한 행동을 추론하여 진행하라.
파일을 직접 읽어 필요한 정보를 파악하라.
</default_to_action>
```

**보수적 행동 (확인 우선):**

```xml
<do_not_act_before_instructions>
명확한 지시 없이는 파일을 수정하지 마라.
의도가 불명확하면 정보 제공과 추천에 그쳐라.
</do_not_act_before_instructions>
```

**비가역적 작업 전 확인 요청:**

```text
로컬·가역적 작업(파일 수정, 테스트 실행)은 바로 진행하라.
비가역적·공유 시스템 영향 작업은 먼저 확인하라:
- 파일/브랜치 삭제, git push --force, DB 테이블 drop
- 외부 서비스 호출 (PR 코멘트, 메시지 전송)
```

### 5. CLAUDE.md 작성 기법

CLAUDE.md는 세션마다 자동으로 주입되는 상시 컨텍스트다. 자주 쓰는 규칙을 등록하면 매번 프롬프트에 반복하지 않아도 된다.

**CLAUDE.md 적합한 내용:**

| 카테고리 | 예시 |
|---|---|
| 빌드/테스트 명령 | `npm test`, `cargo test -- --nocapture` |
| 코딩 규칙 | 들여쓰기, 임포트 순서, 명명 규칙 |
| 아키텍처 규칙 | "비즈니스 로직은 services/ 아래만" |
| 금지 패턴 | "테스트에서 하드코딩 금지", "`any` 타입 금지" |
| 모델 라우팅 | "복잡한 아키텍처 결정은 Opus 사용" |

**CLAUDE.md 구조 예시:**

```markdown
## 빌드
- 테스트: `npm test`
- 타입체크: `npm run typecheck`
- 린트: `npm run lint`

## 코딩 규칙
- 함수형 우선. 클래스는 꼭 필요한 경우만.
- 불변성: 객체 직접 수정 금지. 새 복사본 반환.
- 에러 무시 금지. 명시적 처리 또는 전파.

## 금지
- `console.log` (프로덕션 코드) → `logger.info` 사용
- `any` 타입 → 명시적 타입 정의
- 테스트 파일 수정 없이 테스트 통과 회피
```

> **주의**: CLAUDE.md 200줄 초과 시 준수율 저하. 경로별로 `.claude/rules/` 분산 권장.

### 6. 멀티턴 패턴 — 큰 작업 단계별 분해

CC는 하나의 대화 세션 안에서 여러 턴을 거치며 작업을 진행한다. 큰 작업은 단계로 나눠 요청하는 것이 더 안정적이다.

**권장 분해 패턴:**

```text
# 1턴: 탐색 및 계획 수립
"src/auth/ 디렉토리를 분석하고 JWT 마이그레이션 계획을 작성하라.
아직 파일을 수정하지 마라."

# 2턴: 계획 검토 후 구현
"계획이 맞다. 단계 1(토큰 생성)부터 구현하라."

# 3턴: 검증
"구현 완료. 테스트를 실행하고 실패 원인을 분석하라."
```

**장기 작업에서 상태 유지:**

```text
# 진행 상태 파일 활용
"progress.txt에 현재 진행 상태를 기록하면서 작업하라.
컨텍스트가 초기화되면 progress.txt를 먼저 읽고 재개하라."
```

**멀티 컨텍스트 창 작업 팁:**

| 단계 | 방법 |
|---|---|
| 첫 번째 창 | 테스트 작성, 구조 설계, `tests.json` 생성 |
| 이후 창 | `progress.txt` + `tests.json` + git log 확인 후 재개 |
| 상태 저장 | 구조화 데이터(JSON)로 테스트 결과, 자유 텍스트로 진행 노트 |
| git 활용 | 커밋 로그가 자동 체크포인트 역할 |

---

### 7. 병렬 도구 호출 촉진

CC의 최신 모델은 병렬 도구 실행에 뛰어나다. 명시적으로 촉진하면 속도가 크게 향상된다.

```xml
<use_parallel_tool_calls>
독립적인 도구 호출은 반드시 병렬로 실행하라.
예: 3개 파일을 읽어야 하면 3개 Read 호출을 동시에 실행.
의존 관계가 있는 경우에만 순차적으로 실행하라.
</use_parallel_tool_calls>
```

---

### 8. 과잉 엔지니어링 방지

CC는 요청하지 않은 기능, 리팩토링, "개선"을 추가하려는 경향이 있다.

```text
요청된 것만 변경하라.
- 요청하지 않은 기능, 리팩토링, "개선" 추가 금지
- 변경하지 않은 코드에 주석·타입 어노테이션 추가 금지
- 현재 작업에 필요한 최소한의 복잡도만 사용
- 임시 파일 생성 시 작업 완료 후 삭제
```

---

### 9. 코드 리뷰 하네스

```text
# 버그 탐지 최대화
찾은 모든 이슈를 보고하라. 확신이 없거나 낮은 심각도라도 필터링하지 마라.
각 발견에 신뢰도와 예상 심각도를 포함하라.
커버리지가 목표다: 실제 버그를 놓치는 것보다 이후에 필터링될 발견을 표면화하는 것이 낫다.
```

> Opus 4.7은 "중요한 이슈만 보고하라"는 지시를 이전 모델보다 충실히 따른다. recall을 원하면 필터링 제거를 명시해야 한다.

## 버전별 차이

### 모델별 특성 및 용도

| 모델 | 강점 | CC에서 권장 용도 |
|---|---|---|
| **Opus 4.7** | 장기 에이전틱 작업, 복잡한 추론, 비전, 메모리 | 대규모 코드 마이그레이션, 심층 리서치, 장시간 자율 작업 |
| **Opus 4.6** | 코딩, 도구 사용, 복잡한 문제 해결 | 복잡한 멀티파일 리팩토링, 에이전틱 코딩 |
| **Sonnet 4.6** | 속도·비용 균형, 컴퓨터 사용 | 대부분의 코딩 작업, 인터랙티브 세션 |
| **Haiku 4.5** | 빠른 응답, 저비용 | 단순 검색, 분류, 빠른 질문 |

### Effort 레벨 (v2.1.0+)

`/effort` 커맨드(v2.1.0+)로 추론 깊이를 조절한다.

| Effort | API 값 | 권장 상황 |
|---|---|---|
| 최대 | `max` | 가장 어려운 문제. 과잉 사고 주의. |
| 최고 (신규) | `xhigh` | 코딩·에이전틱 기본값 (Opus 4.7 권장) |
| 높음 | `high` | 지능 민감 작업의 최소 권장치 |
| 중간 | `medium` | 비용 민감 작업 |
| 낮음 | `low` | 단순·짧은 작업, 지연 민감 워크로드 |

```bash
# CC 인터랙티브 모드에서
/effort high

# API 직접 호출 시
output_config={"effort": "xhigh"}
```

> `max`/`xhigh` 사용 시 max output token을 64k 이상으로 설정할 것.  
> 복잡한 문제에서 얕은 추론이 보이면 → 프롬프트 수정보다 effort 올리기가 우선.

### Thinking 설정 변화

| 구분 | 구버전 (4.5 이전) | 현재 (4.6+) |
|---|---|---|
| 설정 방식 | `thinking: {type: "enabled", budget_tokens: N}` | `thinking: {type: "adaptive"}` |
| 제어 방식 | budget_tokens 수동 설정 | effort 파라미터로 제어 |
| 상태 | 지원 (deprecated) | 권장 방식 |

### 모델별 주요 행동 차이

| 행동 | Opus 4.6 | Opus 4.7 |
|---|---|---|
| 지시 해석 | 추론하여 일반화 | 문자 그대로 (범위 명시 필수) |
| 서브에이전트 | 적극적으로 생성 | 기본적으로 덜 생성 (steerable) |
| 도구 사용 | 적극적 | 추론 우선, 필요 시 도구 |
| 과잉 엔지니어링 | 주의 필요 | 덜함 |
| 응답 길이 | 고정 스타일 | 작업 복잡도에 따라 자동 조정 |
| prefill 지원 | 미지원 (4.6+에서 400 에러) | 미지원 |

## 자주 하는 실수

1. **목표만 쓰고 검증 기준 생략** — Claude가 완료를 임의로 판단한다. 항상 "어떻게 확인하는가"를 명시한다.

2. **제안과 구현을 혼동** — "어떻게 하면 좋을까?" 라고 물으면 제안만 한다. 구현을 원하면 "변경하라"고 명령형으로 쓴다.

3. **CLAUDE.md를 200줄 이상 작성** — 준수율 저하. 경로별로 `.claude/rules/`에 분산한다.

4. **긴 문서를 프롬프트 하단에 배치** — 문서는 상단, 쿼리는 하단에 배치해야 최대 30% 성능 향상.

5. **부정 지시만 나열** — "마크다운 쓰지 마라" 대신 "산문 단락으로 작성하라". 긍정 지시가 더 효과적이다.

6. **effort를 낮게 두고 얕은 추론을 프롬프트로 해결 시도** — 복잡한 문제에서 추론이 얕으면 effort를 올려라.

7. **과도한 도구 촉진 문구** — "반드시 이 도구를 써야 한다(CRITICAL)"처럼 강한 언어를 쓰면 4.6+ 모델에서 overtrigger된다. "~할 때 이 도구를 사용하라"로 충분하다.

8. **prefill 사용 (4.6+)** — Claude 4.6 이후 모델에서 마지막 assistant 턴에 prefill을 넣으면 400 에러. 대신 시스템 프롬프트에 "도입부 없이 바로 시작하라" 지시.

9. **테스트 통과를 위한 하드코딩 방지 미명시** — 명시하지 않으면 Claude가 특정 입력에만 동작하는 코드를 작성할 수 있다.

   ```text
   모든 유효한 입력에 동작하는 일반 솔루션을 구현하라.
   테스트 케이스에만 맞는 하드코딩 금지.
   ```

10. **할루시네이션 방지 미명시** — 코드베이스 질문 시 읽지 않은 파일에 대해 추측할 수 있다.

    ```xml
    <investigate_before_answering>
    열어보지 않은 코드에 대해 추측하지 마라.
    사용자가 특정 파일을 언급하면 반드시 먼저 읽어라.
    </investigate_before_answering>
    ```
